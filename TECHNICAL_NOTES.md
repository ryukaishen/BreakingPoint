# BreakingPoint — Technical Notes

This document explains every modelling decision, with the reasons for it, so a judge or reviewer can audit
the system end to end. Code references are relative to the repository root.

## 1. System overview

BreakingPoint is a personalized movement-monitoring platform. Sports map onto reusable movement protocols and
primitives (§11–12); one statistical core and one validated detector serve all of them.

```
             BREAKINGPOINT
                   |
            SPORT PROFILE
                   |
          MOVEMENT PROTOCOL
                   |
             POSE SIGNAL
                   |
            FEATURE VECTOR
                   |
          PERSONAL BASELINE
                   |
           DRIFT DETECTION
                   |
             BREAKINGPOINT
                   ^
                   |
        HiPerGator-calibrated            (BreakingPoint Lab; the currently shipped parameters come from a
         detector parameters              completed 50,000-session local run of the same pipeline)
```

It consists of two cooperating components that share one statistical core:

- **BreakingPoint Edge** (`src/`) — a React + TypeScript single-page app. All inference is on-device:
  MediaPipe Pose Landmarker runs in WebAssembly/WebGL, and everything downstream is plain TypeScript.
  There is no backend.
- **BreakingPoint Lab** (`lab/`, `hpc/`) — Python. It simulates athlete sessions with known change points,
  runs the *same* detector at scale (numpy, Slurm arrays on HiPerGator), and exports the operating
  configuration the app loads (`public/breakingpoint_detector_config.json`).

Single sources of truth:

- `shared/feature_catalog.json` — feature keys, labels, group weights, measurement-noise floors (read by both languages)
- `shared/default_detector_config.json` — pre-validation defaults; replaced at runtime by the Lab export

The three implementations of the statistical core — TypeScript (`src/baseline`, `src/detection`), Python scalar
reference (`lab/breakingpoint_lab/core.py`), and Python vectorized (`lab/breakingpoint_lab/vectorized.py`) —
are tested against each other:

- `lab/tests/test_pipeline.py::VectorizedParityTests` — vectorized == scalar (baselines, LOO reference, drift, alarms, onsets)
- `tests/parity.test.ts` — TypeScript replays `tests/fixtures/parity_fixture.json` (generated by
  `python -m breakingpoint_lab.parity`) across 6 configurations × 16 sessions including missing / low-confidence
  features, and must match to 1e-9 with identical states and alarm reps.

## 2. Edge pipeline

### 2.1 Pose and smoothing (`src/pose/`)

- MediaPipe Pose Landmarker (full model, `runningMode: VIDEO`, GPU delegate with CPU fallback). The WASM
  runtime and `.task` model are copied/downloaded into `public/` by `npm install` (`scripts/setup-assets.mjs`)
  so live mode works offline; a CDN fallback exists.
- **One Euro filter** per landmark coordinate (min cutoff 1.2 Hz, β 0.05): adaptive low-pass that removes jitter
  when a joint is still and keeps lag low during fast movement. Visibility gets an EMA. The filter resets after
  a tracking gap > 0.5 s.

### 2.2 Frame kinematics (`src/biomechanics/frameMetrics.ts`)

Computed in an aspect-corrected image plane (x scaled by width/height):

- knee flexion = 180° − ∠(hip, knee, ankle); hip flexion = 180° − ∠(shoulder, hip, knee) — per side, only if all
  three landmarks have visibility ≥ 0.5;
- trunk lean = angle of the (visibility-weighted) mid-hip → mid-shoulder vector from vertical;
- hip height, ankle height, leg length (hip–ankle distance on the more visible side);
- frame capture quality = mean over shoulder/hip/knee/ankle of the better side's visibility, halved if the body
  is not fully in frame. Labels: Excellent ≥ 0.85, Good ≥ 0.65, otherwise Poor.

These are 2D projected quantities. They are not laboratory-grade joint angles, and are only ever compared with
the same athlete's baseline from the same camera setup, so systematic projection bias largely cancels.

### 2.3 Rep segmentation (`src/reps/segmenter.ts`)

Signal: **d(t) = (hipY − standingHipY) / legLength** — hip drop normalized by the athlete's own leg length
(camera-distance invariant, robust to viewing angle). The standing reference adapts slowly (fast upward,
slow downward) only while the athlete is near standing.

Squat state machine: `STANDING → DESCENDING → (BOTTOM) → ASCENDING → STANDING`.

- enter descent when d > 0.10 for 2 consecutive frames (debounce);
- start/end times = interpolated crossings of d = 0.06 (symmetric, so durations are consistent);
- bottom = time of maximum d; ascent begins when d < max − 0.03 (hysteresis);
- a rep is valid only if max depth ≥ 0.15, and duration is in [0.6 s, 8 s];
- tracking lost > 0.7 s aborts the rep; a > 8 s "rep" triggers re-acquisition of the standing reference.

CMJ state machine: `STANDING → DIP → PROPULSION → FLIGHT → LANDING → STANDING`, with takeoff/touchdown
from ankle lift above the standing ankle height (> 0.035 / < 0.015 leg lengths) and plausibility checks
(flight 0.12–1.0 s).

### 2.4 Per-rep features (`src/biomechanics/repFeatures.ts`)

Squat: L/R knee flexion ROM, hip flexion ROM (more visible side), depth (max d), peak trunk lean, rep /
eccentric / concentric duration, peak knee-extension velocity (central differences on the smoothed knee angle
during the ascent, 3-point moving average), and |L − R| knee ROM asymmetry.

CMJ: jump height (max hip rise ÷ leg length), RSI-modified (jump height ÷ time to takeoff), flight time,
countermovement depth, dip (unweighting + braking) and propulsion durations, peak trunk lean, landing knee
flexion, landing asymmetry.

Every feature has a **quality** in [0, 1] = mean visibility of the landmarks it depends on × frame coverage
(a feature needs ≥ 60 % usable frames in the rep).

## 3. Personalized baseline (`src/baseline/baseline.ts`)

From the calibration reps (≥ 4; the UI asks for 5–8), for each feature with ≥ 3 valid values:

```
center_i = median(x_i)
scale_i  = max( SD_i , 1.4826 · MAD_i , absFloor_i , relFloor_i · |median_i| )
```

- **Median** for location: one odd calibration rep does not move the baseline.
- **max(SD, 1.4826·MAD)**: with 5–8 samples both estimators are noisy; taking the larger is conservative.
- **Floors** (`shared/feature_catalog.json`): the minimum detectable change of a monocular camera — e.g.
  2.5° for knee ROM, 2° for trunk lean, 2 % of leg length for depth, 0.06–0.08 s for durations. Without floors a
  very consistent athlete would get tiny scales and be flagged for sub-noise wobble.

## 4. Movement Drift Score (`src/detection/driftScore.ts`)

```
z_i   = clip( (x_i − center_i) / scale_i , ±zClip )          zClip = 6
drift = sqrt( Σ w_i z_i² / Σ w_i )
w_i   = groupWeight_i × quality_i                              (feature_weighting = grouped_quality)
```

- Group weights stop correlated features from being counted several times (e.g. L knee, R knee, hip ROM and
  depth share the "depth" construct, 0.5 each; trunk lean 1.0; tempo features 0.5 each; asymmetry 0.75).
- Missing-feature handling (selected by the Lab): **drop** — features that are missing or have quality < 0.5 are
  removed and the weights renormalized. The Lab also evaluated *impute* (z = 0) and *skip_rep*.
- If the usable weight covers < 50 % of the available weight the rep is **not scored** (null) — the detector
  then holds its state instead of consuming a falsely precise number.
- The score is the **standardized Euclidean (diagonal-Mahalanobis) distance** divided by √(Σw). A full
  Mahalanobis distance is not used: with 5–8 calibration reps and 10 features the covariance matrix is
  singular. Shrinkage covariance is on the roadmap once more data per athlete exists.
- Explanations: features ranked by |z|; each feature's share of Σ w z² is also stored.

## 5. Athlete-specific in-control reference (leave-one-out)

The detector must know what "normal variation" of the drift score looks like **for this athlete**. With small
samples, an in-sample estimate is optimistic (each calibration rep helped define its own baseline). We use
leave-one-out:

```
for each calibration rep i:   D_i = drift( rep_i | baseline built from the other reps )
μ0 = clamp( mean(D_i), 0.5, 2.0 )
σ0 = clamp( max( SD(D_i), 0.25·μ0 ), 0.2, 0.8 )            (defaults 1.0 / 0.35 if < 3 LOO scores)
```

In the Lab's no-change sessions the resulting standardized drift s = (D − μ0)/σ0 has mean ≈ 0 and SD ≈ 1.1,
i.e. the LOO reference is well calibrated.

## 6. Sequential detection (`src/detection/detector.ts`)

```
s_t  = (D_t − μ0) / σ0           s̃_t = clip(s_t, ±outlierClip)        (unscored reps: state unchanged)
EWMA   Z_t = α s̃_t + (1 − α) Z_{t−1}
CUSUM  C_t = max(0, C_{t−1} + s̃_t − k)
run_t  = number of consecutive reps with s̃ > warningThreshold
```

| mode | BreakingPoint (alarm) | drift emerging (warning) |
|---|---|---|
| `ewma` | Z > breakpointThreshold and run ≥ m | Z > warningThreshold |
| `cusum` | C > h and run ≥ m | C > h/2 |
| `combined` | Z > breakpointThreshold and C > h and run ≥ m | Z > warning or C > h/2 |
| `consecutive` | ≥ max(1, m) consecutive reps with s̃ > breakpointThreshold | s̃ > warningThreshold |

- The alarm **latches** for the set. Warning can return to stable.
- **Onset estimate** = first rep of the current CUSUM excursion (the rep after C was last 0) — the classic CUSUM
  change-point estimator. So BreakingPoint reports both when it became confident (alarm) and when drift likely
  began (onset).
- Winsorizing s and the persistence requirement are what stop one bad rep from triggering.

**Shipped configuration** (chosen by the Lab, `config_id ewma|a=0.4|bp=2|w=1.5|m=2|clip=2.5`):
EWMA, α = 0.4, warning 1.5σ, BreakingPoint 2.0σ, persistence 2 reps, outlier clip 2.5σ, grouped-quality
weighting, drop missing features.

On the Form Drawdown chart the thresholds are drawn in drift-score units, `μ0 + threshold·σ0`, and apply to
the white EWMA line. Bars are the per-rep drift; a bar above the warning line counts as an "elevated rep" for the
persistence rule.

## 7. Recovery check (`src/detection/recovery.ts`)

After rest, three reps are scored against the **original** baseline:

```
excess(x) = max(0, mean(x) − μ0)
recovery% = clamp( 1 − excess(recovery reps) / excess(post-BreakingPoint reps), 0, 1 )
recovered  ⇔ recovery% ≥ 75 % and mean recovery drift ≤ warning level;  partial ⇔ ≥ 40 %;  else persistent
```

In the Lab's scenario H (1,132 sessions), the estimate tracked the simulated truth with Spearman ρ = 0.83
(MAE 14 percentage points; "recovered" status agreed with truth in 80 % of sessions).

## 8. BreakingPoint Lab

### 8.1 Simulator (`lab/breakingpoint_lab/simulate.py`)

Each session draws a synthetic athlete: personal means (knee ROM, hip ROM, depth, trunk lean, eccentric /
concentric / pause durations, structural L/R offset) and personal rep-to-rep variability. Reps are generated
from two latent factors (a "depth" factor and a "tempo" factor) plus feature noise, which gives realistic
within-athlete correlations. Measurement noise mimics pose estimation (noisier when landmark confidence is
low; the far leg is less visible). Values are plausible *relative* magnitudes, not clinical norms.

Fatigue = a per-athlete signature (trunk lean ↑, depth/ROM ↓, concentric slower, asymmetry ↑, eccentric
either way) scaled by a magnitude path m(t) in units of the athlete's own SD.

| scenario | ground truth | purpose |
|---|---|---|
| A no change | — | false-positive rate |
| B isolated bad rep | 1–2 reps of 4–8 SD, then normal | bad rep ≠ fatigue |
| C gradual drift | change at τ, slope 0.25–0.75 SD/rep, peak 1.5–4.5 SD | detection delay |
| D sudden change | step of 1.5–4 SD at τ | rapid detection |
| E camera noise | 2–4× pose jitter, lower confidence (throughout) | robustness to pose noise |
| F landmark dropout | 5–25 % features missing, 10–30 % low-confidence, 2–10 % reps lost | missing data |
| G high variability | 2–3× natural variability | why personal baselines matter |
| H recovery | drift, then return toward baseline (0–80 % residual) | detection + recovery check |

Calibration uses 5–8 reps; sessions have 14–24 monitored reps (26 for H). Seeds:
`SeedSequence([base_seed, shard, block])`.

### 8.2 Sweep and sufficient statistics (`grid.py`, `experiment.py`, `evaluate.py`)

- 5,056 detector settings (EWMA 960, CUSUM 1,152, EWMA+CUSUM 2,916, consecutive 28) × 5 drift-score variants
  (grouped_quality/equal/grouped weighting × drop; grouped_quality × impute/skip_rep) = **25,280 configurations**.
- Drift sequences are computed once per variant per block; all detector settings are evaluated on the same
  sessions (common random numbers) by a detector vectorized across configurations and sessions.
- Each shard stores only counts and integer histograms (detection delay and change-point error in reps), so shards
  merge **exactly** by summation; medians and order-statistic CIs after merging equal those of one giant run.
- Even-numbered blocks = selection split, odd = held-out split.

### 8.3 Metrics

- FPR = fraction of no-change sessions (A, B, E, F, G) with any alarm (Wilson 95 % CI).
- For drift sessions (C, D, H): **detected** (alarm ≥ τ), **early** (alarm < τ, a false alarm), **missed**
  (no alarm); TPR + early + miss = 1.
- Detection delay = alarm − τ; change-point error = |onset − τ| (detected sessions; median with a distribution-free
  order-statistic CI).
- Robustness curves vs noise (throughout and post-calibration), isolated-bad-rep probability, and dropout.

### 8.4 Selection rule (exact)

On the selection split only:

1. Eligible: FPR ≤ 5 % in **every** no-change scenario (A, B, E, F, G).
2. Keep eligible configurations within 2 percentage points of the best eligible miss rate.
3. Choose the lowest median detection delay; ties → lower mean delay → lower pooled FPR → simpler family.

All reported performance comes from the held-out split. A first version of the rule only required pooled
FPR ≤ 5 % (and ≤ 10 % per scenario); it selected a configuration with 9.4 % false alarms on isolated bad reps.
We tightened the rule because "one bad rep shouldn't trigger" is a core product promise; the cost was about
2.4 pp of miss rate and 1 rep of delay (the analysis is reproducible from `results/config_results.csv`).

### 8.5 Results (local workstation, 50,000 sessions; held-out 25,000)

| | value |
|---|---|
| FPR (all no-change) | 2.2 % (2.0–2.4 %) |
| FPR by scenario A / B / E / F / G | 1.4 / 3.9 / 1.6 / 2.3 / 1.8 % |
| detected / early / missed (drift scenarios) | 88.9 % / 0.6 % / 10.6 % |
| detected by scenario C / D / H | 87.0 / 90.2 / 89.6 % |
| median detection delay (C / D / H) | 4 reps (5 / 3 / 4) |
| median change-point error | 1 rep |

Comparisons: the naive "any rep > 2σ" rule had 52.4 % FPR; replacing the personal baseline with population norms
(same detector, evaluation set of 10,000 sessions) raised FPR from 2.2 % to 18.8 % (31.4 % for high-variability athletes)
and cut detection from 88.8 % to 40.5 %.

Robustness (3,000 + 3,000 sessions per level): FPR stays ≈ 1–2 % as pose jitter grows to 5× when the jitter is also
present during calibration (sensitivity drops: detection 87 % → 21 %). If noise increases only **after** calibration,
FPR rises (6 % at 1.5×, 17 % at 2×) — reported as a limitation and the reason for the capture-quality gate and
recalibration advice. With isolated bad reps at 10 % of reps FPR is 5.2 %; with 30 % landmark dropout FPR is 1.0 %
and detection 71 %.

All numbers above come from `results/VALIDATION_REPORT.md` of the run that was actually executed; HiPerGator runs
regenerate the same report at larger scale.

## 9. Demo Mode (`src/demo/`)

A procedural planar-kinematic athlete (shank/thigh/trunk angles, arm counterbalance, a partly visible far leg,
landmark jitter, visibility) emits 33-landmark MediaPipe-format poses at a fixed 30 Hz simulation clock. The
frames enter the same `PosePipeline` → `SessionEngine` as camera frames, so segmentation, features, baseline,
drift and detection are all real. Playback speed only changes how many simulated frames are processed per
timer tick, so results are independent of frame rate. Fatigue presets (`DEMO_PRESETS`) were chosen with
`tests/demo_tune.test.ts` so that the shipped detector tells the intended story. `tests/demo.test.ts` locks it:
reps 1–7 stable, reps 8–9 drift emerging, BreakingPoint at rep 10, onset 6–8, recovery check > 50 %. (Under the
HiPerGator config — warning 1.0σ, BreakingPoint 2.0σ, α 0.4, clip 2.5 — the EWMA can rise at most
`0.4·2.5 + 0.6·Z` per rep, so from a stable rep (Z ≤ 1.0) it needs at least three reps to exceed 2.0σ:
"1–8 stable, 9 drift, 10 BreakingPoint" is unreachable for any data, and the demo tells the closest story.)

## 11. Sport profile abstraction

BreakingPoint is organized as **SPORT → PROTOCOL → PRIMITIVE → shared statistical core** (`src/protocols/`):

| layer | file | what it defines | what it must NOT define |
|---|---|---|---|
| Movement primitive | `primitives.ts` | segmentation phases, live phase labels, the engine (segmenter + feature extractor) if implemented | detector parameters |
| Movement protocol | `protocols.ts` | a repeatable screen on one primitive: status (READY / BETA / COMING_SOON / FUTURE), camera placement, purpose, measured feature keys | detector parameters |
| Sport profile | `sports.ts` | which protocols a sport recommends, sport-specific screen names, featured metrics, feature terminology, drift-pattern names, demo session labels | detector parameters, feature weights |
| Launch | `launch.ts` | `resolveLaunch(sport, protocol, sub)`: the only path from a selection to a runnable engine; returns `null` for unknown or roadmap protocols | — |

Design rules:

- **One detector.** Every launch uses the single `DetectorConfig` loaded at startup (the Lab export). Sport profiles
  contain no detector fields; a test fails if any sport config mentions EWMA, CUSUM, thresholds, alpha or clipping, and
  another asserts that every launchable context runs with an identical config.
- **Display-only customization.** Feature weights in the drift score are *not* changed per sport: the detector's
  calibration assumes the catalog weights, and per-sport reweighting would invalidate it. Sports change only which
  metrics are featured, what they are called, and how drift patterns are named. "What changed" is always ranked by
  the true |z|.
- **Status gates launch, not the primitive.** `canLaunch(p)` requires READY/BETA *and* an implemented primitive. Approach
  Jump uses the implemented jump primitive but is COMING_SOON, so it cannot start; this is tested.
- **Same primitive, same pipeline.** Soccer and volleyball demos produce identical drift sequences (tested); only the
  context (labels, featured metrics, athlete card) differs.

Drift-pattern labels (`patterns.ts`): each feature of each primitive maps to a movement family and a direction that
counts as drift for that family (e.g. CMJ jump height ↓ → explosive; lunge recovery velocity ↓ → recovery; trunk lean ↑ →
technique; asymmetry ↑ → asymmetry). Over the reps since the estimated onset, each family scores the mean of its two
largest directional |mean z|; the top family names the pattern if its score ≥ 1.5. Otherwise, if the last five drift
scores vary more than 2 σ₀, the pattern is *movement variability increasing*. A secondary family is reported when it
scores ≥ 75 % of the top one. Sports may rename a family (basketball: *jump consistency drift*; volleyball: *landing
mechanics drift*) but cannot change which family the data selects. Labels are descriptive and non-medical.

## 12. Movement primitives

| primitive | status | segmentation | features |
|---|---|---|---|
| `SQUAT` | implemented (reference) | hip-drop state machine (§2.3) | §2.4 |
| `JUMP_AND_LAND` | implemented | dip → propulsion → flight → landing from ankle lift (§2.3) | §2.4 |
| `FORWARD_LUNGE` | **beta** | the squat's hip-drop state machine with `LUNGE_THRESHOLDS` (min rep 0.8 s): ready → descent → bottom → recovery | L/R knee ROM, lead-hip ROM (lead leg = the foot that travels), lunge depth, step length (max ankle separation ÷ leg length), trunk lean, rep / descent / recovery duration, peak recovery velocity (hip-rise rate, leg lengths/s), L/R difference |
| `LATERAL_MOVEMENT`, `SINGLE_LEG_HOP`, `GAIT_CYCLE`, `HIP_HINGE`, `STRIKE_STEP`, `KICK` | roadmap | — | — |

**Why this avoids a model per sport.** Fatigue detection here is not classification. It is change detection relative
to the athlete's own baseline, so there is nothing sport-specific to train. What differs between sports is *which
repeatable movement* is observed. A small set of primitives covers many sports: the jump primitive serves soccer,
basketball, volleyball, gymnastics and field sports; the lunge primitive serves pickleball, tennis, badminton, fencing and
strength. Adding a sport is a configuration change. Adding a primitive means adding a segmenter, a feature extractor,
catalog entries with measurement floors, a synthetic demo generator and tests; the baseline, drift score and detector are
reused unchanged.

**Lunge implementation and validation status.** The synthetic lunge athlete plants both feet and solves each leg with
two-link inverse kinematics (knees flex anteriorly). The lead foot steps out, the hip drops, and the rear heel rises.
It uses a separate code path, so the squat/CMJ demo random sequences are byte-identical to before (their story tests are
unchanged). Through the full pipeline it segments all 6 + 14 + 3 demo reps, a single malformed lunge does not trigger,
and progressive drift fires at rep 10 with pattern *recovery slowing*. Real-camera reliability (alternating legs, rear-foot
occlusion, frontal drift) has not been established, so it is labeled BETA.

**Detector calibration scope.** The Lab calibrates the detector at the movement-signal level, on simulated squat feature
vectors. The standardized, athlete-calibrated drift score (LOO reference) is what makes the detector transferable across
primitives. Sport-specific and primitive-specific clinical validation is future work. The Lab pipeline was deliberately
not modified to support UI sports.

## 13. Known limitations

- Monocular 2D kinematics: out-of-plane motion and far-limb occlusion; only within-person comparisons are made.
- Forward lunge is beta: verified on deterministic synthetic data, not yet on a corpus of real camera recordings; the
  protocol asks athletes to lead with the same leg every rep.
- CMJ features do not include knee/hip ROM during the countermovement; adding them would change the validated CMJ drift
  score composition, so it is deferred.
- Capture changes after calibration (camera moved, lighting) look like drift; recalibrate.
- Calibration is short (5–8 reps), so the baseline is uncertain; floors and the LOO reference mitigate this.
- The Lab validates statistical behaviour on synthetic data. It does not establish clinical validity. The next
  step is a prospective study against motion capture / force plates and real fatigue protocols.
- BreakingPoint does not diagnose, predict injuries (including ACL tears), or replace professionals.
